# ECU参照定数・VANOS対応・実車基準点の確認

2026-10-29。既存BIN・コード・原ログだけで確認できる範囲を完了した。ソルバー／長時間計算／ECU書込み・指令は0回。元BIN・ログ・旧試験アーカイブは変更していない。

## 結論と前回記録の更新

**ECU固定参照量606.056 mg/気筒を実BINで確認し、VANOSのソフト上の表示変換を確定した。一方、実機カムの物理原点と走行時BINの同一性、定常の実車基準点は未確定。** 次は長時間計算ではなく、同じBIN・時刻・位相・環境で比較できる収録契約を整える。

前回のVE_DEFINITION_THERMAL_REVIEW_2026-10-29.mdではraw診断角とspreadの関係を未確認としていた。今回はXDF、rawマップ、ECU処理、decoderを照合し、**吸気display = live + 70、排気display = 128 − live**を確認した。前回のraw対spreadの直接差は物理位相差として使わず、本報告の変換後比較へ更新する。旧記録を上書きせず、追加証拠として保存する。

これは「診断角に70/128を付ければ実測最大リフト角が保証される」という意味ではない。ソフト座標の変換と、実車カムのTDC・最大リフト・sensor trim・学習値の物理対応を区別する。

## 1. ECU参照定数：実バイトから確認

| 項目 | XDF／64KB partialのoffset | バイト | BE整数／換算 |
|---|---|---|---|
| K_RF_HUBVOLUMEN | 0xD21C | 0C 81 | 3201 / 1000 = 3.201 dm³ |
| K_RF_LUFTDICHTE | 0xD21E | 04 70 | 1136 / 1000 = 1.136 kg/m³ |
| 固定参照質量 | 上記積／6気筒 | — | **606.056 mg/気筒** |

確認したのはFull 211323000401PD31_TERRA.bin、uploaded_mss54.bin、session-920-base.bin、旧worktree側uploadedの4パス・3種類のSHA。すべて上記4バイトは一致した。uploadedのSHAは`1ea646589b87e7ffb3dd691221a51ffd3e2f51a602be17c52ee1ea4fd24c8b9d`、session920-baseは`2c9cac6be29a10a2de4b15ed7d718cee1c56db4f0918bc1a29f96a02249c0d6a`で異なる。

Fullの校正領域をpartialと同じ並びに取り出すと、uploadedと148バイト、session920-baseと1684バイト違う。定数が同じことは全校正・走行時BINの一致を意味しない。7月ログにBIN SHAがなく、これらのどれが当該走行時の校正かは確定できない。Fullのプログラムをpartialだけの実車と完全同一と断定しない。

Fullのrf_init（file 0x2181C）の実バイトを逆アセンブルし、runtime 0x8D21E/0x8D21Cの乗算、整数除算、m_norm/m_norm_faktへの格納を確認した。算術結果はm_norm=10890、m_norm_fakt=10813。公称参照606.056 mgと、整数計算・DS2量子化を経たML換算は厳密には同じ値ではない。例としてRF100%、3900rpmではMLraw=1698、decoder換算424.50 kg/h。公称参照量による連続式は425.451312 kg/h。この差をVE予測誤差とみなさず、ECUの整数算術として区別する。

## 2. RFとMLを独立な実測同士として使わない

Fullのrf_calc（file 0x218D0）は、モード／補正からRFを求めた後、**ML = N × trunc(RF × m_norm / 1000) / 25000**を整数演算で作る。DS2側はMLに0.25を掛けてkg/hへ復号する。

保存4ログのN>0等で演算可能な4489行中3716行で、この整数式とMLがraw count単位で完全一致した。残りも含めた差はlog_evidence.jsonに保持し、非一致を勝手に補正していない。非一致の原因をすべて時刻差と断定することも避ける。

旧backend/scripts/validate_drive_log.pyは高い相関から「rf IS the MAF measurement」と表示するが、この判定では因果方向を区別できない。**RFから作ったMLを独立MAF計測の証拠にしてはならない。** 今回そのスクリプトを実機妥当性検証として実行・採用せず、ローカルコードと実バイトの証拠を記録した。RFが実測センサ補正を含む場合でも、MLとの相関だけで独立精度は検証できない。

## 3. VANOS：raw、表示、物理角を分離

| 層 | 吸気 | 排気 |
|---|---|---|
| XDF rawマップ | signed 8-bit、degree単位 | signed 8-bit、degree単位 |
| XDF表示 | **70 + raw** | **128 − raw** |
| 通常目標処理 | (補間raw + K_EVAN1_SOLL_OFFSET) ×10 | (補間raw + K_AVAN1_SOLL_OFFSET) ×10 |
| DS2 live復号 | signed BE16 ×0.1、追加定数なし | signed BE16 ×0.1、追加定数なし |
| 試験設定に相当するlive | display70 → **0°** | display87 → **41°** |

SOLL_OFFSETは今回確認BINで双方0。制御モード、暖機、レート制限、上下限、学習・診断指令の枝では単純なrawマップ補間と最終目標は一致しない。このレビューのマップ照合は浮動小数bilinear比較であり、その全分岐をbit-exactに再演したものではない。

sensor位置計算は別処理で、K_*_OFFSET、歯位置・歯周期、補間位置、ADAPを合算してISTを得る。Fullは基準trimが吸気+3°／排気−2°、uploadedとsession920-baseは吸気−2°／排気+1°。この違いも、参考Fullと車両校正を混同できない根拠になる。

現generatorはMOPを吸気360+display、排気360−displayとし、さらにoffsetとdeltaを引く。固定offset・durationの下では、live値を+1°すると両側とも生成MOPは+1°、つまり遅いクランク位相へ移る。「live増加＝吸気進角」と名前だけで判断しない。

ただしECUのISTにはsensor trimが既に入るため、live由来MOPへtrimを再適用すると二重計上になる可能性がある。実機の機械的基準との関係が未確定なので、今回は符号反転・trim削除・位相合わせの変更をしていない。必要な物理照合はMEASUREMENT_REQUIREMENTS.mdに具体化した。

## 保存マップに見つかった不一致

app/data/csl_ecu_maps.jsonとBIN由来displayを全256セルずつ比較した。排気256セルは一致。吸気は255セル一致し、**5000rpm・RO 1.599121%の1セルがBIN raw50→display120°に対しJSON130°**だった。RPM軸は一致し、RO軸には最大0.001465 percentage pointの丸め差がある。

この1セルは現在の3900rpm／全開試験に対応するセルではなく、その試験差の原因とは主張しない。JSON全体をBINの完全な写しとみなすことはできないので、今回のログ比較にはraw BINから読んだ軸と表を使用した。元JSONを上書きせず、差分とcalibration_snapshot.jsonを保存した。検証結果は「照合実施・不一致あり」とし、全一致に書き換えていない。

## 4. 実車基準点の整理

7月のwebserial原ログ4本・4497行を時刻順に調べ、既存条件（3900±5%、RO≥85%、水温≥75℃）の15候補を再同定した。前後行の変化率も原時系列で計算し、抽出後の点同士を隣接とみなしていない。

| 項目 | 15候補の実績 |
|---|---|
| 連続候補群 | 9群、各1～2点、最長**0.4481秒** |
| rpm／実スロットル | 3724～4091／95.8～100.7%（表示値） |
| 前行からの回転変化率 | **−2109～+820 rpm/s** |
| IAT | 43～55℃。計算入口約25℃とは異なる |
| 吸気display実角 | **69.1～107.2°**、計算70°との差−0.9～+37.2° |
| 排気display実角 | **86.8～108.0°**、計算87°との差−0.2～+21.0° |
| 吸気実／目標差 | 最大絶対**22.8°** |
| 排気実／目標差 | 最大絶対1.6° |

これにより、前回のrawとspreadの直接比較で大きく見えていた定数差を除けた。一部は試験設定に近い実角だが、同じ定常条件を持続した基準点とは認定できない。暫定収録screenでも瞬時全条件一致は0、まして持続・反復・不確かさの確認はない。

追加で手元のsession920/923/954の4つのfixtureも確認した。idle/低負荷・上限2390rpmで、間引きや事前フィルタ済みのものを含む。3900rpm全開の不足を埋める原時系列ではない。PCの全ログを無制限探索したとは主張せず、今回使用したパス・範囲をsources.jsonで固定した。

旧ログはblock3/19/35を順次取得して最後の1時刻で統合し、raw payloadとblock別時刻を保持していない。過去のpayload再復号や厳密な同期復元はできない。RFは0.1ポイント、IAT1℃、大気圧3mbarという刻みもあり、0.1%効果の実証には取得・不確かさ設計を別に要する。

## 次に実行する価値のある作業

1. **ログとBIN・定義・block時刻を結び付ける入力／収録契約の実装を優先。** 既存JSONの無条件利用を避け、BIN SHAとマップ差分検出を付ける。追加通信より、現在の通信のpayloadと時刻保存を先に検討する。ECU RFへの整合と、独立新気VEの検証を出力名で分ける。
2. **同条件の基準点を実測できる準備。** 計測項目、初期screen、最低持続・反復、λと燃料補正の区別、実VANOS基準、独立空気量の不足を別紙に固定した。現在のログに合格を与えない。実車／計器を要する部分を資料不足のまま推測で補完しない。
3. **長時間の格子・周期追加は引き続き不要。** 現在の定義・同期・実車条件の欠落を追加約5.96時間／2N4N一対では解消できない。今回の有限試験の未達、実機精度未証明、暫定候補探索という利用制限は維持する。

本依頼の「既存BINとログで確認できるところまで」と不足計測条件の記録は完了。新しい収録実装・実車計測・物理モデル修正は今回実施していない。
